Spacing & Margin Audit — Menus and Navigation

oslo.town iOS · branch oslo-reskin · audited 2026-11-09 against HEAD d4d3848c3 · artifact only, no changes applied

This is an audit of every menu or navigation surface in the app against the project's design tokens (Spacing / Radius in Common Components/AlignmentGuides.swift). For each surface it records the current state (Before), a recommendation (After), and — in the final section — a numbered work order with exact old_string → new_string pairs that an LLM (or human) can apply mechanically, including guards and verification steps.

0. Token reference (single source of truth)

Spacing: xs=4   s=8   m=12   l=16   xl=24   xxl=32        // layout scale
Radius:  xs=4   s=8   m=12   l=16   xl=24   pill=999      // corner scale
ButtonPadding: vertical=3, horizontal=Spacing.s, capsuleHorizontal=Spacing.l
maxFeedContentWidth = 700;  spacingBetweenGutterAndContent = Spacing.s

House rules inferred from the token migration (commits cb1e11895…90fea8ee6):

  • Use Spacing.* for every padding/margin/gap that is layout spacing. Bare .padding() (implicit 16) is not tokenized even though its value equals Spacing.l — the number is invisible to token greps and to future value retunes.
  • Control metrics (icon frame sizes, circle diameters, hero heights) are not spacing tokens — they stay as component constants unless they repeat across components (see §10).
  • Feed content rows use symmetric horizontal gutters of Spacing.m (commit 01070464f).

Verdict: the FAB's position is tokenized (good, and the comment documents the physics); the raws are control metrics, not layout spacing, so they do not violate the token system. The one wart is the compound expression Spacing.xxl + Spacing.l + Spacing.m — three tokens summed to express a single clearance number, which breaks if any scale step retunes (the Day-4 "global retune" hook).

7. Trend Board DECISION

Current state § TrendBoardView.swift:217, 269

.padding(EdgeInsets(top: Spacing.s, leading: Spacing.l, bottom: Spacing.s, trailing: Spacing.l))  // rank rows + header rows

The board's horizontal gutters are Spacing.l (16) while feed rows, after the Day-4 gutter pass (01070464f), use symmetric Spacing.m (12). So a post in the timeline and a ranked tag sitting on the very same screen-width don't share a content edge — the board's text starts 4pt further out. The Day-4 note says "Directory/TrendBoard spacing untouched" — i.e. the divergence is known, not accidental.

// Recommended (consistency-first): align to the feed gutter system
.padding(EdgeInsets(top: Spacing.s, leading: Spacing.m, bottom: Spacing.s, trailing: Spacing.m))
// Consequences: rows get 4pt tighter to the screen edge — matches every timeline row on Feed/Oslo.
// If the board should feel MORE airy than feeds (deliberate contrast), instead keep l/l and record
// that decision as a comment here, so the next audit doesn't re-flag it.

Chip hairlines § TrendBoardView.swift:337, 346 intentional — keep

.padding(EdgeInsets(top: 1, leading: Spacing.xs + 1, bottom: 1, trailing: Spacing.xs + 1))

The 1 values are optical hairlines tying the chip border to the text — they are deliberately not on the layout scale. Keep, but note that Spacing.xs + 1 is again compound arithmetic; if more chips appear, consider a chipInset = Spacing.xs + 1 named constant.

Priority: P2 — visual change, needs your call (see §11 work order item 5).

13. What this audit deliberately did NOT flag

  • System-styled chrome (segmented controls, Form rows, UIContextMenu content, sidebar) — platform-owned, not ours to tune.
  • Content-row internals (post cards, media, polls) — retuned in earlier passes; separate concern.
  • Typography sizes (.font metrics) — a scale hook could be added to AlignmentGuides later, but no raw-size cleanup is urgent.
  • Control metrics retained as component constants: 24pt icon slot, 50pt FAB circle, 72pt toolbar host, 110pt profile banner, 400×500 language popover — each is a named, single-purpose dimension, not a layout gap.
