Explore › Hashtags — three rework concepts

The current page is a flat list of trending tags from /api/v1/trends/tags — hashtag, follow state, nothing else. Two facts shape the redesign: (1) every tag arrives with 7 days of history (posts + participants per day), so ranking, momentum and sparklines are free client-side; (2) on a small instance the raw trend list is dominated by federated noise (#silentsunday, #lfc, #rodelijn) — the page needs an Oslo lens, not a bigger list. What X, Bluesky and Threads each do differently is the third input.

Concept A

Trend Board — ranked, with a memory

Inspired by X/Twitter's Trending tab: a ranked board with counts, rank movement and a "what's happening" feeling — but built entirely from the data Mastodon already sends.

What it adds over today
Rank numbers, participants (not just posts), 7-day sparklines, rank movement ("↑2" = today's bucket vs yesterday's, computed client-side), and a Today / This Week toggle that re-ranks from the same history array.
The Oslo lens
A pinned "From people here" section first: tags that local accounts (the Directory curator graph, or simply local-timeline participants) actually used today — then the federated noise below under "Elsewhere". Solves the #lfc problem without any server change.
Engineering
cheap100% client-side: existing trends API + Tag.history. The current HashtagRowView becomes a richer row; the segmented picker stays. No new timeline plumbing.
Cost / risk
~1-2 days. Sparkline deltas look sparse on tiny days (12 posts) — design must normalize. The local/federated split needs one cheap source: whether the tag has posts in the local timeline cache, or a per-day "local uses" can't be derived — worst case the split is heuristic (tag known to be used by local accounts you follow).
Concept B

Topic Guides — curated, not crawled

Inspired by Threads' "Today's topics": AI-clustered topic cards with tap-through feeds. Oslo.town takes the editorial route it already loves (Directory = @matt's curation): topics are defined by a curator, each guide is a bundle of hashtags + a merged feed.

What it replaces
The flat tag list becomes curated topic cards. Each guide = emoji tile, title, curator byline, participant count ("63 people today" — summed across the bundle's tags from their history), and the member tags. Tap opens a merged multi-tag timeline.
The merge is the interesting bit
Mastodon has no multi-tag timeline API, but the app can fetch each member's hashtag timeline in parallel and merge-by-date client-side (dedupe by post id). 4-6 tags is fine. This also unlocks "topic feed" elsewhere later (e.g., pinned to the Feed picker).
The Oslo lens
Bundles are a curation artifact — either defined in-app (config list in DiscoveryType, like directoryCuratorAcct already works) or, nicer, stored on the curator's Mastodon server as lists or collections the app fetches — zero app updates to change the guides, same philosophy as the Directory.
Engineering
mediumMerged timeline type (new MastodonTimelineType case + merge loader), topic model + fetch (in-app config to start), new cards on top of existing rows for a "Trending beyond the guides" tail.
Cost / risk
~3-5 days. Curation burden lands on a human (that's the point, but it must be low-effort or it rots). Merged feeds paginate awkwardly (N link headers) — load-first-20-of-each-and-merge is good enough.
Concept C

The Live Pulse — velocity, not volume

Inspired by Bluesky's trending (velocity-ranked, minimal, refreshes in place). Built on something Mastodon apps never use: the app now has a streaming connection (shipped for the feed), and every streamed post arrives with its hashtags.

What it replaces
Instead of the server's daily trend rollup, the app keeps a rolling window counter fed by everything that passes through it: home stream (already live), Oslo tab stream, and the Everything stream while you browse. Tags are ranked by velocity (posts per hour) over the last ~3-6 hours, with follow-graph context lines.
Three scopes, one honest story
Around you = tags from your home stream (who you follow actually shapes it). oslo.town = the Oslo tab's public:local stream (the community pulse — small numbers, worn proudly: "6 posts/h" is true here). Fediverse = the Everything stream, which replaces the server's noisy trend list with what your own firehose shows.
The Oslo lens
Built in. The oslo.town scope is the lens. Small-instance numbers stop being embarrassing because the design treats velocity as the story, not raw counts vs. Twitter-scale.
Engineering
ambitiousAn in-memory tag/aggregator over streamed posts (phase-2 infrastructure makes this real: every update event already carries the post JSON), plus a discrete session store so the window survives restarts. New ranked list UI. No API or server changes.
Cost / risk
~5-8 days. Honest limits: the window only sees what the app sees (no stream open → no data; cold start needs a backfill from trend history). Aggregation bugs (tag normalization) are the classic trap. The "LIVE" claim needs the streaming phase-3 groundwork to hold while browsing Explore.

Recommendation: B is the identity move and A is the quick win — they also compose well: A's ranked board underneath, B's curated guides on top, giving the page both a live floor and an editorial face. C is the most original (nobody in the Mastodon app ecosystem has a stream-fed live tag pulse) but stands on phase-3 streaming and session aggregation, so it's a second-quarter project. A sensible order: B → A → C.
